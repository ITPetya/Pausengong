# Pausengong — Handoff

Status as of **2026-08-31**. Read this first before touching the code.

## What this is

A C#/WinUI 3 rewrite of an older Python break-bell script (not included in this repo). All PCs on the LAN are peers; the first one to start becomes "Chef" and hosts an embedded MQTT broker. Config (schedule, rooms, room-mode, test-mode) syncs across all PCs over MQTT. Ships as one self-contained `.exe` — no installer, no pre-installed .NET/runtime needed on the target machine.

Full original spec and architecture decisions: `partitioned-baking-garden.md` (same repo, top level).

## Where things are

- **Source**: this folder (`src/Pausengong.Core` = platform-agnostic logic, `src/Pausengong.App` = WinUI3 UI, `tests/Pausengong.Core.Tests` = xUnit, 82 tests as of 2026-10-19 — see Verification status below for which of those have actually been run vs. only compiled).
- **The exe to actually run/hand out**: not built by default — run `packaging\publish.ps1` (added 2026-10-19, wraps the command below and fails if the output is anything other than the single exe):
  ```
  dotnet publish -c Release -r win-x64 -p:WindowsAppSDKSelfContained=true -p:WindowsPackageType=None -p:PublishSingleFile=true --self-contained true -o publish
  ```
  Output: `publish\Pausengong.App.exe` (~300MB, one file, nothing else needed). `publish/` is gitignored — regenerate it, don't expect it to already exist after a fresh clone. `packaging\publish.ps1` itself has **not been run anywhere** — this tool environment has no Windows, so it is unverified (Vermutung, not Annahme) beyond being a mechanical wrapper around the exact command above; run it once on a real machine before relying on it.
- **Dev-loop build** (`dotnet build`) lands in `src\Pausengong.App\bin\x64\Release\net8.0-windows10.0.19041.0\win-x64\Pausengong.App.exe` — multi-file, faster to produce, fine for iterating, **not** what you'd give someone else (loose Content files get silently dropped by single-file publish — see Gotchas below, this is why assets are embedded now).
- Git repo, `master` branch only, no remote configured yet.

- **Phase 6 (real draw/fallback logic)**: **done** (2026-08-28). `BreakTimeWatcher` (the old "every node rings itself locally, unconditionally" first cut) is deleted — replaced end to end:
  - `Pausengong.Core/Scheduling/DrawService.cs` — pure/stateless: shuffles a room's currently-available members, returns a `DrawResult` (drawn node + full fallback candidate order).
  - `Pausengong.Core/Scheduling/BreakScheduler.cs` — per configured break time: T-60s draw (per room, among available members), T-10s recheck (replaces the pick if it went offline, redraws fresh if nobody from the original order is left), T-0 ring — walks the room's whole candidate order, one at a time, until someone confirms or the room is out of candidates. Only runs while `isSelfChief()` is true — the Chef is the sole authority so nodes don't race each other. Every dependency (availability lookup, send, wait-for-confirm) is a plain delegate, not a concrete MQTT type, which is what makes it fully unit-testable with `TimeProvider` + fakes, no real timers/network — see `BreakSchedulerTests.cs`.
  - `Pausengong.Core/Scheduling/RingConfirmationTracker.cs` — per-node pending-confirm wait with a `TimeProvider`-based timeout.
  - `Pausengong.Core/Scheduling/RingCoordinatorService.cs` — the MQTT glue: every node (regardless of Chef status) subscribes to its own `ring/target/{nodeId}` and rings through `RingExecutor` (the safety gate is untouched) when a command arrives, then publishes `ring/confirm/{nodeId}`; only starts a `BreakScheduler` internally to actually drive the timeline. "Availability" is deliberately *not* a separate network poll (no `AvailabilityPoller` class, unlike the plan's original naming) — it's read straight from the already-live `NodePresenceService.KnownNodes` registry, since that already gives real-time online status and a second ping-pong protocol would just be redundant.
  - Also broadcasts a non-retained `ring/draw-preview` (`DrawPreviewEntry` list: room + drawn node + resolved hostname/IP label) on every draw/recheck/ring-resolution — every node receives it, which is what feeds `MainViewModel.NextGongTargetText` (the subtitle under the "Pausengong" title): shows "RoomName: NodeLabel" per room once a draw exists for the upcoming break, or who actually rang last time once a cycle resolves; "–" before the first draw of the day.
  - **Fixed (2026-08-31)**: `RingCoordinatorService`/`ConfigSyncService`/`NodePresenceService` used to use a "subscribe once, guarded by a bool" pattern that skipped re-subscribing after a Chef handover reconnects to a brand-new broker session — since `MqttNodeClient.ConnectAsync` always connects with `WithCleanSession(true)`, a reconnect wipes server-side subscriptions even though the guard bool stayed `true` from the first connect, so a node would silently stop receiving config/presence/ring messages after any handover past the first. Fixed by removing the guard in all three services — they now resubscribe on every call (`OnConnectedAsync`/`StartAsync`), which is safe since MQTT re-subscribing to an already-subscribed topic is a no-op server-side. `RingCoordinatorService.StartAsync` still only starts the `BreakScheduler` once (that part of the guard was correct — a reconnect shouldn't spawn a second scheduling loop). Covered by new tests: `ConfigSyncServiceTests.OnConnectedAsync_CalledAgainAfterReconnect_ResubscribesToEveryTopic`, `RingCoordinatorServiceTests.StartAsync_CalledAgainAfterReconnect_ResubscribesButDoesNotRestartScheduler`, and a new `NodePresenceServiceTests.cs` (previously had zero coverage).
  - **Fixed (2026-08-31) — real-world bug report from the maintainer**: "4 break times configured, one PC online, nothing ever rang." Root cause: `BreakScheduler` only ever draws/rings against `_configStore.Current.Rooms.Rooms`, and **no room existed** — rooms were an opt-in manual step (drag a node onto a room you first had to create via "Raum hinzufügen"), and a fresh/older config's `Rooms` list is empty by default. With zero rooms, the per-room loop in `RunDraw`/`RunRecheck`/`RunRingAsync` silently iterates nothing, forever — no error, no toast, nothing, regardless of schedule or how many nodes are online. Fixed properly (not a scheduler-level hack) by making rooms non-optional: `RoomConfig` now has a well-known **`Standardraum`** (`RoomConfig.DefaultRoomId`/`DefaultRoomName`) that always exists — `AppConfig.CreateDefault()` seeds it, and `ConfigStore.LoadAsync` self-heals any already-saved config missing it (in-memory only, `UpdatedAt` left untouched so a healed empty-room config can never out-prioritize a peer's real room setup during MQTT last-writer-wins sync — see `RoomConfig.IsMissingDefaultRoom`). The old "Nicht zugeordnet" pseudo-list (`MainViewModel.UnassignedNodes`, a `ListView` in `MainPage.xaml`) is gone entirely, replaced by this real, persisted room: every newly seen node lands there automatically (`MainViewModel.AssignUnknownNodesToDefaultRoom`, called from both `ApplyRooms` and presence-change handling) until a human drags it into a custom room. It shows up as an ordinary room card in the UI except its "✕ löschen" button is hidden (`RoomViewModel.IsDefaultRoom`/`DeleteButtonVisibility`) — deleting it would leave nothing for new nodes to land in. Deleting any *other* room now moves its nodes into Standardraum instead of an unassigned limbo. Covered by `ConfigStoreTests.LoadAsync_WhenNoFileExists_ReturnsDefaultWithTestModeOnAndOneDefaultRoom` and `LoadAsync_SelfHealsAnExistingConfigWithZeroRooms_ByAddingTheDefaultRoomInMemory`.
- **Phase 7 (automatic room detection)**: **in progress — original ultrasonic approach dropped**, replaced (2026-08-28, the maintainer's call) by BLE-RSSI-based "neighborhood clustering". Of the build order below, steps 3–4 (the fully agent-buildable, hardware-independent half) are **done** (2026-08-31): `Pausengong.Core/Neighbors/NeighborGraphBuilder.cs` (aggregation — symmetrizes per-node RSSI reports, averaging both directions when known, flagging one-directional-only pairs via `NeighborEdge.IsBidirectional`) and `Pausengong.Core/Neighbors/ClusterCalculator.cs` (threshold-graph + connected-components clustering, threshold passed in, not hardcoded), both pure/static and fully unit-tested (`NeighborGraphBuilderTests.cs`, `ClusterCalculatorTests.cs`) with synthetic RSSI data. `TopicSchema.NodeAudioPing`/`NodeAudioResult` (stale ultrasonic-era stubs) removed, replaced with `TopicSchema.NodeBleNeighbors`/`NodeBleNeighborsWildcard`. **Not started**: steps 1–2 (real BLE send/receive — needs actual hardware, see Phase 0 spike below) and step 5 (wiring clusters into `RoomModeConfig`/UI). See "Phase 7 replacement" section below.
- **Phase 8 (MSIX packaging)**: **not started**. The self-contained exe path (primary requirement) works; Store packaging is untouched. Note: may become a hard prerequisite for Phase 7's replacement — see below.

## Phase 7 replacement: BLE neighborhood clustering (planned 2026-08-28; aggregation/clustering built 2026-08-31)

### Why the pivot

The original Phase 7 (ultrasonic room detection: emit a tone, fingerprint via mic capture) is dropped. the maintainer's call, 2026-08-28: too many technical and environmental problems (device mic/speaker quality and placement varies per PC, ambient noise, reflections/reverberation — none of that is solvable in software alone). Replacement idea, spec'd by the maintainer via a prompt he had another LLM draft: PCs broadcast their identity over **Bluetooth Low Energy (BLE)** and listen for each other; signal strength (RSSI) between a pair approximates physical proximity, since walls attenuate BLE meaningfully. Group PCs into anonymous **neighborhood clusters** (not named "rooms" — no manual naming needed) purely from the resulting signal-strength graph. No new hardware may be purchased.

### Hard constraint the original prompt violates — do NOT build it as given

the maintainer's source prompt specifies a **Python** agent (`bleak` library) per PC plus a separate **central aggregator** process/server. **Do not build that.** This app has been a single self-contained `.exe`, no separate runtime, no extra process, since Phase 0 (see "Environment needed to build" above) — a Python agent on every PC breaks that outright: a second runtime to install, a second process to keep alive, a second deployment/config story disconnected from the rest of the app. Everything below re-derives the same functional idea (broadcast + RSSI + clustering) natively in C#/.NET inside `Pausengong.Core`/`Pausengong.App`, reusing the *existing* Chef/MQTT infrastructure as the "central aggregator" instead of inventing a new server — there already is one authority node (the Chef) doing exactly this kind of coordination for `BreakScheduler`.

### Architecture

1. **Phase 0 — hardware/API spike, do this FIRST, before writing any real logic.** Two real unknowns that could each independently block this whole approach:
   - Does `Windows.Devices.Bluetooth.Advertisement.BluetoothLEAdvertisementPublisher` (send) / `BluetoothLEAdvertisementWatcher` (receive — exposes `RawSignalStrengthInDBm` per received advertisement) actually work from this app's **unpackaged** build (`WindowsPackageType=None`)? Some WinRT APIs require MSIX package identity to function correctly, and this project has deliberately avoided MSIX so far (Phase 8 untouched). If these need packaging, either do Phase 8 first or fall back to a lower-level Win32 Bluetooth API path (unscoped, more work).
   - Do the actual target PCs even have a Bluetooth radio? Plausible for laptops, **not guaranteed for office desktop PCs** — "keine zusätzliche Hardware" only works if the hardware is already physically there. the maintainer should check the real machines before this gets built out.
   - Concretely: a throwaway spike exe (same pattern as the original Phase 0 WinUI3 spike) that publishes an advertisement and watches for others, logging RSSI to console on two real PCs — confirm they see each other and that "same room" vs. "through a wall" produces a plausibly different RSSI.

2. **Node identity broadcast**: reuse the existing `NodeIdentity.NodeId` (already a stable per-machine GUID, persisted locally). A legacy BLE advertisement payload is small (~31 bytes) — encode a short/truncated form (e.g. first 8 hex chars, or a manufacturer-data section), not the full GUID; only needs to disambiguate within one LAN-sized deployment.

3. **Local collection loop, every node, always running** (same "runs uniformly on every node" shape as `RingCoordinatorService`'s ring/target handling) — **not started, needs real BLE hardware/API access (Phase 0 above)**:
   - Advertiser publishes continuously; watcher listens continuously.
   - Raw BLE RSSI is noisy — smooth per observed node (short moving average or median-of-last-N over ~30s), don't act on single instantaneous readings.
   - Every ~30s, publish this node's current `{observedNodeId: smoothedRssi}` map (`NeighborReport`, already exists in `Models/NeighborReport.cs`) over MQTT on `TopicSchema.NodeBleNeighbors` (added 2026-08-31), non-retained (live telemetry, not status to replay to late joiners).

4. **Aggregation — the Chef's job**, same authority pattern as `BreakScheduler` (no new "central server" concept needed): subscribe to `TopicSchema.NodeBleNeighborsWildcard`, build a symmetric adjacency structure per node pair. **Done (2026-08-31)**: `Pausengong.Core/Neighbors/NeighborGraphBuilder.cs` — pure static `BuildEdges(IReadOnlyCollection<NeighborReport>)`, averages both directions when both are available (BLE RSSI isn't perfectly symmetric A→B vs. B→A — radio/antenna differences), and flags a one-directional-only report as weaker/provisional evidence via `NeighborEdge.IsBidirectional`. Unit tested (`NeighborGraphBuilderTests.cs`) with synthetic reports; no MQTT wiring yet (that's part of step 3/the still-missing "Chef subscribes and calls this" glue, analogous to `RingCoordinatorService`).

5. **Clustering — keep it simple, no ML dependency.** Build a graph with an edge between two nodes iff their symmetrized RSSI is above a configurable threshold (must be calibratable per deployment/hardware — expose as a setting, don't hardcode a magic dBm value without on-site tuning), then compute **connected components** over that thresholded graph. **Done (2026-08-31)**: `Pausengong.Core/Neighbors/ClusterCalculator.cs` — pure static `Cluster(allNodeIds, edges, thresholdRssiDbm)`, threshold is a parameter (no hardcoded value — on-site calibration still needed once real hardware is in play), a node with no qualifying edge comes back as its own singleton cluster rather than being dropped. This is a deliberately simpler stand-in for the DBSCAN/Louvain suggestion in the maintainer's source prompt: threshold-graph + connected-components *is* essentially single-linkage clustering with `eps` = the RSSI threshold. Unit tested (`ClusterCalculatorTests.cs`): same-cluster via direct edge, transitive connection through a middle node with no direct edge, threshold boundary (`>=` included), multiple isolated clusters, and the all-isolated/no-edges case. Only reach for something heavier (a real DBSCAN/Louvain NuGet package) if simple thresholding measurably misbehaves in practice — don't pre-optimize for that.

6. **Feeding into rooms**: this is what the already-existing-but-unwired `RoomModeConfig`/`RoomMode` (`Pausengong.Core/Config/RoomModeConfig.cs`, `Models/RoomMode.cs` — both exist today, **zero UI anywhere** references them) is for. In "automatisch" mode, the Chef periodically recomputes clusters and publishes them as `RoomGroup`s (auto-named "Cluster A"/"Cluster B"/… or similar) over the *existing* `ConfigSyncService`/`ConfigRooms` channel — no new sync mechanism needed, just a new producer of room config alongside (or instead of) manual drag-and-drop. Needs: a UI toggle for manual/automatic mode (currently missing entirely), and a way to keep a human-renamed cluster from snapping back to "Cluster A" on the next recompute (e.g. only auto-rename clusters that don't already have a human-assigned name). **Not started.**

### Testability

Steps 4–5 (aggregation math + clustering) are pure and fully unit-testable with synthetic RSSI matrices, no real Bluetooth hardware needed — same approach as `DrawServiceTests`, and now actually built that way (see above). Steps 1–3 (real BLE send/receive) fundamentally need real hardware and are human-verified only, exactly like the dropped ultrasonic Phase 7 was flagged as "not agent-verifiable" — that constraint doesn't go away with the BLE pivot, it just moves to different hardware, and is why steps 1–2 below are still untouched.

### Suggested build order for whoever picks this up

1. Phase 0 spike above — resolves the two biggest unknowns before anything else gets built. **Still pending — needs the maintainer on real hardware.**
2. `Pausengong.Core/Neighbors/`: `BleAdvertiser`/`BleWatcher` behind an interface, so the collection loop can eventually be unit tested against a fake — same seam pattern as `IMqttNodeClient`/`IUdpDiscoveryTransport`. **Interfaces + fakes done (2026-10-19)**: `IBleAdvertiser`/`IBleWatcher` (`Pausengong.Core/Neighbors/`), `FakeBleAdvertiser`/`FakeBleWatcher` (tests). **Real implementation still not started** — deliberately: blocked on step 1's outcome, writing it now would be guessing at whether the WinRT API even works in an unpackaged app.
3. Neighbor-report MQTT plumbing — **the Chef-side glue is done (2026-10-19)**: `NeighborAggregatorService` (`Pausengong.Core/Neighbors/`) subscribes to a track's wildcard topic, feeds `NeighborGraphBuilder`/`ClusterCalculator`, exposes `LatestClusters` + a `ClustersChanged` event. Generic over topic/threshold so one class serves both tracks (see Track B below) — not yet wired into DI/`App.xaml.cs`, since nothing real publishes to either topic yet (step 2 above, and Track B step 3) and there's no UI consumer yet (step 5 below). Unit tested against `FakeMqttNodeClient` (`NeighborAggregatorServiceTests.cs`), including that the two tracks never cross-contaminate when sharing one MQTT client.
4. Aggregation + threshold-graph clustering in Core, fully unit tested. **Done (2026-08-31)**, field names generalized 2026-10-19 (see Track B step 4) — see steps 4–5 above.
5. Wire into `RoomModeConfig` + a new "automatisch" UI toggle that auto-publishes `RoomGroup`s. **Not started.**

Real BLE send/receive and the DI/UI wiring still don't exist — only the pure/hardware-independent pieces above (interfaces, fakes, the aggregator, the clustering math) do, per the maintainer's explicit instruction (2026-08-28: "plane das nur ein", reaffirmed 2026-10-19 for Track B: plan first, then only build what doesn't need unavailable hardware to write or verify).

### Track B: ultrasonic presence sensing (added 2026-10-19, build and test alongside BLE, not instead of it)

the maintainer's call, 2026-10-19: build **both** detection tracks and compare them on real hardware himself, rather than deciding on paper which one wins. Trigger: he found `https://ultramodem.ronen.in/` (`github.com/ronen6999/ultramodem`), a browser-based near-ultrasonic data link (binary FSK, 18500 Hz = `0` / 19500 Hz = `1`, ~20 bit/s, XOR checksum only, no FEC/retry, max 64 chars), and asked whether it revives the ultrasonic room-detection idea dropped on 2026-08-28.

**Assessment of that project (for the record, this is an opinion, not a measurement):** it does not demonstrate what we'd need. It is a deliberate, human-held, one-pair, quiet-room *data transfer* toy — no amplitude-to-distance metric, no multi-device collision handling, and the author states the tone is "audible to most people" even at those frequencies. None of that proves or disproves whether continuous, unattended, multi-PC amplitude sensing is viable here — it just sidesteps the exact problems (ambient noise, mic/speaker placement/quality, reflections) that killed the original ultrasonic Phase 7. Noted so the reasoning is on record; **the maintainer wants both tracks built and tested empirically regardless, not re-decided from this analysis alone** — that is his call to make, not something to re-litigate at planning time.

**Design — deliberately not a port of ultramodem's protocol.** Ultramodem's FSK/checksum/bitrate exist to move a text payload; we don't need a data channel, only a per-pair proximity signal, same as the BLE track's RSSI. Porting FSK bit-encoding here would add complexity (symbol timing, checksum framing) that buys nothing for this use case. Proposed instead:

1. **Phase 0 — hardware/perception spike, do this FIRST, same spirit as the BLE Phase 0 spike:**
   - Does a single fixed near-ultrasonic tone (candidate: ~19 kHz, pick after checking the actual frequency response of the target PCs' built-in speakers/mics — cheap integrated hardware often rolls off well before 20 kHz, this must be measured, not assumed) survive office background noise through a **real** PC microphone at usable SNR?
   - Is a tone repeating every ~30s (matching the BLE report cadence) perceptible/annoying to anyone actually sitting near a PC, over a full work day, on the real target hardware? This is a human-judgment question, not something to assume answered either way from ultramodem's "audible to most, inaudible to some" framing.
   - Concretely: a throwaway spike exe, same pattern as the BLE one, playing a candidate tone and logging captured amplitude on two real PCs a room apart and a wall apart — plus the maintainer/a colleague just sitting near it for a while and saying whether they notice it.

2. **Collision handling — the one thing ultramodem never had to solve and we do:** multiple PCs cannot all chirp at once on one shared tone and expect a meaningful amplitude reading. Reuse the existing Chef-as-authority pattern (same shape as `BreakScheduler`/the BLE aggregation plan): the Chef publishes a deterministic round-robin order (e.g. sorted known `NodeId`s from `NodePresenceService.KnownNodes`) and a fixed slot duration; during its own slot, each node plays the single tone and every other node's listener records the amplitude it measured during that slot, attributed to that slot's known sender. Time-division, not frequency-division — no per-node frequency allocation needed, which also sidesteps tightly packing many sub-bands into a narrow near-ultrasonic range.
3. **Local sense loop, every node:** continuously-running microphone capture (`NAudio.Wave.WaveInEvent`, already have NAudio as a dependency for `GongPlayer`) + FFT magnitude at the chosen tone frequency, smoothed the same "short moving average, don't act on one instantaneous reading" way as the BLE RSSI plan. **Seam done (2026-10-19):** `IUltrasonicBeacon` (`Pausengong.Core/Audio/`, play-tone / listen-and-measure) + `FakeUltrasonicBeacon` (tests), same seam pattern as `IMqttNodeClient`/`IUdpDiscoveryTransport`. **Real NAudio-based implementation and the loop itself are not started** — deferred, not blocked the same way BLE is (no open API-availability question here, NAudio capture/playback doesn't care about packaging), but still needs real speaker/mic hardware to write and verify correctly, and the concrete tone frequency is a Phase 0 output, not something to guess at here.
4. **Reuse, don't duplicate, the aggregation/clustering math.** **Done (2026-10-19):** `NeighborReport.ObservedSignalByNodeId`, `NeighborEdge.SymmetrizedSignal`, and `ClusterCalculator.Cluster`'s `threshold` parameter are renamed from their old BLE-specific names (`ObservedRssiByNodeId`/`SymmetrizedRssi`/`thresholdRssiDbm`) — purely a rename, behavior unchanged, existing BLE tests updated in place. Both tracks now feed the same `NeighborGraphBuilder`/`ClusterCalculator`/`NeighborAggregatorService` pipeline. **Do not merge BLE and ultrasonic edges into one clustering pass** — dBm and tone-amplitude-ratio are different, incomparable scales; `NeighborAggregatorService` is instantiated once per track specifically so this can't happen by accident (see step 3 of the BLE "Suggested build order" above) — run two independent clusterings and let the maintainer compare the two *results* on real hardware, don't average their inputs.
5. **New MQTT surface, mirroring the BLE one. Done (2026-10-19):** `TopicSchema.NodeUltrasonicNeighbors(nodeId)`/`NodeUltrasonicNeighborsWildcard` (non-retained per-node report, same shape as `NodeBleNeighbors`) plus `TopicSchema.UltrasonicSchedule` (the Chef-published round-robin schedule topic). The schedule computation itself is also done: `UltrasonicRoundRobinSchedule` (model) + `UltrasonicRoundRobinScheduler.BuildSchedule` (`Pausengong.Core/Neighbors/`) — pure, deterministic (ordinal node-id sort), computes who transmits at any instant and when each node's own slot starts; fully unit tested (`UltrasonicRoundRobinSchedulerTests.cs`). **Not done:** nothing calls `BuildSchedule` from a running Chef yet, and nothing publishes/subscribes to `TopicSchema.UltrasonicSchedule` yet — that glue needs the real `IUltrasonicBeacon` implementation (step 3) to be worth wiring up.
6. **Feeding into rooms:** identical to the BLE track's step 6 — both are just alternate producers of candidate `RoomGroup`s under the existing `RoomModeConfig`/"automatisch" mechanism (still needs the UI toggle, see Suggested next steps). A real decision on whether the UI lets the maintainer pick BLE vs. ultrasonic vs. manual, or auto-prefers whichever one actually produced a result, is **not made yet** — surface this as an explicit choice when the UI toggle gets built, don't default it silently.

**Testability:** step 4's math is pure/unit-testable exactly like the BLE track, with synthetic amplitude data standing in for real captures — and step 5's schedule computation now actually is unit tested, not just claimed to be testable. Steps 1–3 (real tone playback/capture) need real hardware and are human-verified only — same constraint as the BLE track's steps 1–3, it doesn't go away here either. **Caveat on all the "done" items above:** this tool environment has no Windows and no `Microsoft.WindowsDesktop.App` runtime (required because the TFM is `net8.0-windows10.0.19041.0`), so `Pausengong.Core` was only cross-compiled here (confirmed: builds with 0 errors), not actually test-run — `dotnet test` itself needs to happen on a real Windows machine before trusting that the new tests pass, not just that they compile.

No code exists yet for this track either — planning only, per the same "plan it first" instruction that applied to the BLE track.

## Critical safety rule — do not break this

`Pausengong.Core/Config/TestModeState.cs` + `RingExecutor.cs` are the safety-critical gate: **test mode defaults to ON** on any fresh config, and only the toast/notification path may fire for scheduled/networked rings. The manual "Test-Gong" button is the *only* thing allowed to bypass this, and only from its own direct UI click handler — never from scheduling, config sync, or startup code. The user was explicit about this (real break-bell system, accidental real gong during dev/testing is genuinely disruptive). If you add new ring-triggering code, it must go through `RingExecutor.ExecuteRingAsync`, not call `IGongPlayer` directly.

## Update notification system (added 2026-10-19)

The maintainer's request, 2026-10-19: no in-app installer/auto-updater (stays consistent with "ships as one self-contained exe, nothing else to install" — see "What this is" above), but the running app should know when it's outdated, tell the user with an urgency appropriate to how serious the update is, and — for the most serious case — refuse to fully load until updated.

**Where the version info lives:** `/version.json` at the repo root (plain public file, fetched over HTTPS from `raw.githubusercontent.com` — no auth, no GitHub API, no rate limits to worry about at this scale):
```json
{
  "latestVersion": "1.0.0",
  "urgencyScore": 1,
  "message": "Aktuell.",
  "downloadUrl": "https://github.com/ITPetya/Pausengong/releases/tag/dev-latest"
}
```
**`urgencyScore` is 1-3, travels with the version, not derived from it** (exactly the maintainer's spec) — only the person cutting a release knows whether it's UI-only or fixes something that affects compatibility/reliability:
- **1 (Informational)** — simple, dismissible notice. App loads completely normally.
- **2 (Important)** — more prominent notice (an orange/warning-colored `InfoBar` instead of a blue one). Still never blocks anything.
- **3 (Mandatory)** — compatibility/reliability at risk. The app does **not** fully load: see "Mandatory block" below.

**Must-bump-together discipline:** `Pausengong.App.csproj`'s `<Version>` (the running exe's own version, read via `Assembly.GetExecutingAssembly().GetName().Version`) and `/version.json`'s `latestVersion` have to move together on every release that changes behavior, or the whole mechanism silently does nothing (a build whose own version already matches "latest" always reports up-to-date, correctly, but uselessly if nobody bumped the manifest). **This is the maintainer's explicit instruction, 2026-10-19: whoever is pushing changes owns keeping both in sync** — not something to defer to a separate release-manager step. **This was not actually followed for five commits straight** after the system was built — the maintainer caught it ("du solltest sie doch auf dem laufenden halten") when the displayed version never moved despite substantial changes shipping. Bumped to `1.1.0` (both places) at that point to cover everything since `1.0.0`: the update system itself, all of the room-visualization work, and the stale-label/Settings-window bug fixes. Going forward, bump on every push that changes behavior — do not let this lapse again.

**Core (`Pausengong.Core/Updates/`), fully unit-tested, the usual seam pattern:**
- `UpdateManifest`/`UpdateUrgency`/`UpdateCheckResult` — the data shapes.
- `UpdateChecker.Compare(Version current, UpdateManifest?)` — pure comparison, **fails open on every ambiguous input** (missing manifest, unparsable version string, current already newer than "latest" — can happen during local dev): all resolve to "up to date", never to "update needed"/mandatory by default. This is deliberate and important: Pausengong is a LAN-only break-bell system that must keep working with zero internet access, so a failed/garbled fetch (no network, GitHub down, a typo in the JSON) must never be the reason it fails to start or rings late.
- `IUpdateManifestFetcher`/`HttpUpdateManifestFetcher` — the real one does a plain `HttpClient` GET, swallows every exception and returns `null` instead of throwing (same fail-open reasoning).
- `UpdateService` — composes fetch + compare into the one call the App layer actually makes; has its own defensive `try/catch` around the fetcher call too, in case some future fetcher implementation doesn't honor the "never throw" contract.

**App layer:**
- `App.xaml.cs`'s `OnLaunched` now runs the update check **before any window exists** (`LaunchAsync`). A `Mandatory` result shows `UpdateRequiredWindow`/`UpdateRequiredPage` **instead of** `MainWindow` — no `ConfigStore`, no MQTT, no election, no scheduling loop ever starts in that path, only the update notice itself (two buttons: "Update herunterladen" opens `DownloadUrl` via `Windows.System.Launcher`, "Beenden" exits). Anything else (no update, Informational, Important) loads `MainWindow` completely normally, with the check result carried into `MainViewModel` to show as an `InfoBar`.
- Bottom-right of the main window: small grey `v1.0.0` text (`MainViewModel.CurrentVersionText`), overlaying the whole window (`Grid.RowSpan` over every row) so it always sits in the actual corner regardless of room-visualization content. Tap re-runs the check (`CheckForUpdatesCommand`) and always reports something back — an `InfoBar` for an available update, a toast ("Pausengong ist aktuell") if not.
- `MainWindow.ShowFromTray()` (i.e. "beim Öffnen des Fensters", the maintainer's second explicit trigger) also re-checks, via `MainViewModel.RefreshUpdateStatusSilentlyAsync()` — same check, but doesn't toast "up to date" on every single tray-restore, only opens the `InfoBar` if something's actually found.
- A `Mandatory` result discovered this way (while already running, not at startup) obviously can't retroactively un-load the app — it just becomes the strongest non-blocking `InfoBar` severity (`Error`) at that point; the actual blocking only happens at the one gate in `App.xaml.cs`.

**Verification status:** `UpdateChecker`/`UpdateService` are fully unit-tested (10 tests: version comparison, urgency mapping and clamping, fail-open on null/throw) — same caveat as everything else Core, compiled here, not executed (no Windows). The App-layer wiring (DI, `MainViewModel`, the two new windows, the `InfoBar`/version-text XAML) has **not been built or run anywhere** — same "no way to verify WinUI3 here" limitation as the room visualization, compounded by the fact that `UpdateRequiredWindow` in particular (the one path that matters most, since it's the one that can block the app) has never been exercised even once. Before trusting this: bump `version.json` to something newer than the installed build's own version with `urgencyScore: 3` and confirm `UpdateRequiredWindow` actually shows up and actually prevents the normal window/networking from starting.

## Non-obvious gotchas hit while building this (read before re-deriving)

- **MQTTnet 5.x has no managed/auto-reconnect client** — `MQTTnet.Extensions.ManagedClient` stopped being published after 4.3.7 and doesn't exist for v5. Reconnect policy is hand-rolled in `ChefElectionService` (driven by `MqttNodeClient.Disconnected`), which is actually correct here since after a Chef dies you need to re-run discovery, not blindly retry the dead server.
- **WinUI3 `Window` is not a `FrameworkElement`** — `x:Bind` with a `Converter=` on anything hosted directly in a `Window`'s XAML crashes natively (`0xc000027b` in `Microsoft.UI.Xaml.dll`, no useful .NET exception). Fix: host all real content in a `Page` (`MainPage`, `SettingsPage`), keep `Window` XAML nearly empty, set `Content = new SomePage(...)` in code-behind.
- **Missing `XamlControlsResources` merge in `App.xaml`** causes the same native crash class the moment a `ThemeResource` like `CardStrokeColorDefaultBrush` is referenced (e.g. `BorderBrush` on a `ListView`). Must merge `<XamlControlsResources xmlns="using:Microsoft.UI.Xaml.Controls" />` in `App.xaml` resources — normally scaffolded automatically by the VS project template, which we don't have here.
- **`x:DataType` on a BCL value type (e.g. `TimeOnly`) in a `DataTemplate`** is unstable — crashed (same `0xc000027b` signature) the moment the template actually got instantiated (i.e., only when the list went from empty to non-empty, not on load). Avoid; use the default `ToString()` rendering (works fine, already proven) or a wrapper view-model type instead.
- **`dotnet publish -p:PublishSingleFile=true` silently drops plain `<Content>` items** (tested repeatedly, including with `CopyToPublishDirectory` set — didn't help) from the output — a `bin\...\win-x64` build has `Assets\gong.wav` etc., a single-file `publish\` output does not. Fixed by embedding these 4 files (`gong.wav`, `Logo.ico`, `Logo-256.png`, `Logo-44.png`) as `<EmbeddedResource>` with explicit `<LogicalName>`, extracted once to `%LocalAppData%\Pausengong\assets\` on first run (`AssetExtractor.cs`). If you add new runtime assets, embed them the same way — don't add more loose `<Content>` files expecting them to survive single-file publish.
- **Multiple instances on one PC fight over the same UDP 49531 / MQTT 18830 ports** and the losing instance's startup exception was previously swallowed silently (fire-and-forget `Task`, not routed through `Application.UnhandledException`), leaving the UI stuck forever on "Netzwerk wird gesucht …" with zero indication anything failed. Fixed two ways: (1) a named `Mutex` in `App()` refuses a second launch outright (shows a native `MessageBox`, points at the tray icon); (2) `MainPage.StartNetworkingAsync` now has a top-level `try/catch` that surfaces the failure in `MainViewModel.NextGongTargetText` (the subtitle line under the "Pausengong" title) and logs to `%LocalAppData%\Pausengong\logs\`. If you see "Netzwerk-Start fehlgeschlagen: ..." in the UI, that log has the real exception.
- There's also an app-wide `Application.UnhandledException` handler (logs + `e.Handled = true`) as a last-resort safety net for UI-thread exceptions specifically — it does **not** catch background `Task` exceptions (different mechanism), which is why the fix above was still needed separately.
- **`string.GetHashCode()` is randomized per process in .NET** (hash-flooding DoS mitigation, on by default since .NET Core) — a preventive note, not something actually hit yet: anything that needs the *same* string to map to the *same* bucket/shape/slot across app restarts (e.g. `RoomViewModel.Shape`, picked once per `RoomId`) must NOT use the built-in `GetHashCode()`, or it silently picks something different every time the process restarts. `RoomViewModel.StableHash` is a plain unseeded hash for exactly this reason — if you need the same pattern elsewhere, reuse that approach, don't reach for `GetHashCode()`.
- **`GridView` and `ListView` share the `ListViewBase` base class** but are not interchangeable in a cast: `OnRoomDrop`'s `(ListView)sender` broke the moment the room visualization (2026-10-19) switched the device grid from `ListView` to `GridView` for its auto-wrap layout — fixed by widening the cast to `(ListViewBase)sender`, which both event-handler-attached controls satisfy. If you swap which concrete `ListViewBase` subclass something is, grep for narrow casts on its `sender`.
- **A C# `record`'s implicit copy constructor can make `new(null)` ambiguous** — `DeskSlot(NodeListItem? Node)` (`DeskSlot.cs`) also gets a compiler-generated `DeskSlot(DeskSlot original)` copy constructor for free, and `null` converts equally well to either reference-type parameter, so `new DeskSlot(null)` fails with `CS0121` ("ambiguous between..."). Real CI build failure, 2026-10-19 — the first thing in the whole room-visualization effort actually disproven by a real build rather than only reasoned about. Fix: an explicit cast, `new((NodeListItem?)null)`. Applies to any single-parameter record with a nullable reference-type (or nullable-anything) parameter.
- **`Canvas.Left`/`Canvas.Top` set on an element INSIDE an `ItemsControl`'s `DataTemplate` has no effect, regardless of binding syntax** — the spiral room layout (2026-10-19) needed two real screenshots and two separate fix attempts to get right, both informative:
  - **First (wrong) theory**: `Canvas.Left="{x:Bind Left, Mode=OneWay}"` on the DataTemplate's root `Grid` compiled and built cleanly on real CI, but a screenshot showed every room stacked at the same position. Diagnosed (incorrectly, as it turned out) as "`x:Bind` on an attached property doesn't reliably apply at runtime" — a real, documented WinUI3/UWP issue in general, just not what was actually happening here — and "fixed" by switching to plain `{Binding}`. A second screenshot showed the *exact same* stacked result, disproving that theory.
  - **Actual root cause**: when `ItemsControl` generates items into a `Canvas` `ItemsPanel`, each `DataTemplate` instance is wrapped in an implicit `ContentPresenter` — and THAT, not anything inside the `DataTemplate`, is the real direct child of the `Canvas`. `Canvas.Left`/`Top` only affects a `Canvas`'s direct children, so setting it one level too deep (on the template's own root element) is inert no matter what binding mechanism is used — both attempts were fixing the wrong symptom.
  - **Real fix**: `ItemsControl.ItemContainerStyle`, a `Style TargetType="ContentPresenter"` with `Setter`s for `Canvas.Left`/`Canvas.Top` — the standard, long-documented WPF/UWP/WinUI pattern for positioning `ItemsControl` items on a `Canvas`. `Setter.Value` only supports plain `{Binding}`, never `{x:Bind}` (a `Style` isn't tied to one `DataTemplate`'s compiled-binding scope the way `x:Bind` requires) — so the "switch to `{Binding}`" half of the first fix attempt was actually correct, it just needed to be applied in the right place (the container's style, not the template's content).
  - **Neither XML well-formedness checking (`xml.etree.ElementTree`) nor a successful CI build can catch this class of bug** — both only prove the markup parses and compiles, never that a specific binding actually takes effect at runtime or targets the element that's actually arranged by its parent panel. If positioning a `Canvas`-hosted `ItemsControl` item ever looks wrong again, check `ItemContainerStyle` first, not the binding syntax.
