# Pausengong — Handoff

Status as of **2026-08-31**. Read this first before touching the code.

## What this is

A C#/WinUI 3 rewrite of an older Python break-bell script (not included in this repo). All PCs on the LAN are peers; the first one to start becomes "Chef" and hosts an embedded MQTT broker. Config (schedule, rooms, room-mode, test-mode) syncs across all PCs over MQTT. Ships as one self-contained `.exe` — no installer, no pre-installed .NET/runtime needed on the target machine.

Full original spec and architecture decisions: `partitioned-baking-garden.md` (same repo, top level).

## Where things are

- **Source**: this folder (`src/Pausengong.Core` = platform-agnostic logic, `src/Pausengong.App` = WinUI3 UI, `tests/Pausengong.Core.Tests` = xUnit, 72 tests as of 2026-10-19 — see Verification status below for which of those have actually been run vs. only compiled).

  dotnet publish -c Release -r win-x64 -p:WindowsAppSDKSelfContained=true -p:WindowsPackageType=None -p:PublishSingleFile=true --self-contained true -o publish

## Phase 7 replacement: BLE neighborhood clustering (planned 2026-08-28; aggregation/clustering built 2026-08-31)

### Why the pivot

The original Phase 7 (ultrasonic room detection: emit a tone, fingerprint via mic capture) is dropped. the maintainer's call, 2026-08-28: too many technical and environmental problems (device mic/speaker quality and placement varies per PC, ambient noise, reflections/reverberation — none of that is solvable in software alone). Replacement idea, spec'd by the maintainer via a prompt he had another LLM draft: PCs broadcast their identity over **Bluetooth Low Energy (BLE)** and listen for each other; signal strength (RSSI) between a pair approximates physical proximity, since walls attenuate BLE meaningfully. Group PCs into anonymous **neighborhood clusters** (not named "rooms" — no manual naming needed) purely from the resulting signal-strength graph. No new hardware may be purchased.

### Hard constraint the original prompt violates — do NOT build it as given

the maintainer's source prompt specifies a **Python** agent (`bleak` library) per PC plus a separate **central aggregator** process/server. **Do not build that.** This app has been a single self-contained `.exe`, no separate runtime, no extra process, since Phase 0 (see "Environment needed to build" above) — a Python agent on every PC breaks that outright: a second runtime to install, a second process to keep alive, a second deployment/config story disconnected from the rest of the app. Everything below re-derives the same functional idea (broadcast + RSSI + clustering) natively in C#/.NET inside `Pausengong.Core`/`Pausengong.App`, reusing the *existing* Chef/MQTT infrastructure as the "central aggregator" instead of inventing a new server — there already is one authority node (the Chef) doing exactly this kind of coordination for `BreakScheduler`.

### Architecture

1. **Phase 0 — hardware/API spike, do this FIRST, before writing any real logic.** Two real unknowns that could each independently block this whole approach:
   - Does `Windows.Devices.Bluetooth.Advertisement.BluetoothLEAdvertisementPublisher` (send) / `BluetoothLEAdvertisementWatcher` (receive — exposes `RawSignalStrengthInDBm` per received advertisement) actually work from this app's **unpackaged** build (`WindowsPackageType=None`)? Some WinRT APIs require MSIX package identity to function correctly, and this project has deliberately avoided MSIX so far (Phase 8 untouched). If these need packaging, either do Phase 8 first or fall back to a lower-level Win32 Bluetooth API path (unscoped, more work).
   - Do the actual target PCs even have a Bluetooth radio? Plausible for laptops, **not guaranteed for office desktop PCs** — "keine zusätzliche Hardware" only works if the hardware is already physically there. the maintainer should check the real machines before this gets built out.
   - Concretely: a throwaway spike exe (same pattern as the original Phase 0 WinUI3 spike) that publishes an advertisement and watches for others, logging RSSI to console on two real PCs — confirm they see each other and that "same room" vs. "through a wall" produces a plausibly different RSSI.

2. **Node identity broadcast**: reuse the existing `NodeIdentity.NodeId` (already a stable per-machine GUID, persisted locally). A legacy BLE advertisement payload is small (~31 bytes) — encode a short/truncated form (e.g. first 8 hex chars, or a manufacturer-data section), not the full GUID; only needs to disambiguate within one LAN-sized deployment.

3. **Local collection loop, every node, always running** (same "runs uniformly on every node" shape as `RingCoordinatorService`'s ring/target handling) — **not started, needs real BLE hardware/API access (Phase 0 above)**:
   - Advertiser publishes continuously; watcher listens continuously.
   - Raw BLE RSSI is noisy — smooth per observed node (short moving average or median-of-last-N over ~30s), don't act on single instantaneous readings.
   - Every ~30s, publish this node's current `{observedNodeId: smoothedRssi}` map (`NeighborReport`, already exists in `Models/NeighborReport.cs`) over MQTT on `TopicSchema.NodeBleNeighbors` (added 2026-08-31), non-retained (live telemetry, not status to replay to late joiners).

4. **Aggregation — the Chef's job**, same authority pattern as `BreakScheduler` (no new "central server" concept needed): subscribe to `TopicSchema.NodeBleNeighborsWildcard`, build a symmetric adjacency structure per node pair. **Done (2026-08-31)**: `Pausengong.Core/Neighbors/NeighborGraphBuilder.cs` — pure static `BuildEdges(IReadOnlyCollection<NeighborReport>)`, averages both directions when both are available (BLE RSSI isn't perfectly symmetric A→B vs. B→A — radio/antenna differences), and flags a one-directional-only report as weaker/provisional evidence via `NeighborEdge.IsBidirectional`. Unit tested (`NeighborGraphBuilderTests.cs`) with synthetic reports; no MQTT wiring yet (that's part of step 3/the still-missing "Chef subscribes and calls this" glue, analogous to `RingCoordinatorService`).

5. **Clustering — keep it simple, no ML dependency.** Build a graph with an edge between two nodes iff their symmetrized RSSI is above a configurable threshold (must be calibratable per deployment/hardware — expose as a setting, don't hardcode a magic dBm value without on-site tuning), then compute **connected components** over that thresholded graph. **Done (2026-08-31)**: `Pausengong.Core/Neighbors/ClusterCalculator.cs` — pure static `Cluster(allNodeIds, edges, thresholdRssiDbm)`, threshold is a parameter (no hardcoded value — on-site calibration still needed once real hardware is in play), a node with no qualifying edge comes back as its own singleton cluster rather than being dropped. This is a deliberately simpler stand-in for the DBSCAN/Louvain suggestion in the maintainer's source prompt: threshold-graph + connected-components *is* essentially single-linkage clustering with `eps` = the RSSI threshold. Unit tested (`ClusterCalculatorTests.cs`): same-cluster via direct edge, transitive connection through a middle node with no direct edge, threshold boundary (`>=` included), multiple isolated clusters, and the all-isolated/no-edges case. Only reach for something heavier (a real DBSCAN/Louvain NuGet package) if simple thresholding measurably misbehaves in practice — don't pre-optimize for that.

6. **Feeding into rooms**: this is what the already-existing-but-unwired `RoomModeConfig`/`RoomMode` (`Pausengong.Core/Config/RoomModeConfig.cs`, `Models/RoomMode.cs` — both exist today, **zero UI anywhere** references them) is for. In "automatisch" mode, the Chef periodically recomputes clusters and publishes them as `RoomGroup`s (auto-named "Cluster A"/"Cluster B"/… or similar) over the *existing* `ConfigSyncService`/`ConfigRooms` channel — no new sync mechanism needed, just a new producer of room config alongside (or instead of) manual drag-and-drop. Needs: a UI toggle for manual/automatic mode (currently missing entirely), and a way to keep a human-renamed cluster from snapping back to "Cluster A" on the next recompute (e.g. only auto-rename clusters that don't already have a human-assigned name). **Not started.**

### Testability

Steps 4–5 (aggregation math + clustering) are pure and fully unit-testable with synthetic RSSI matrices, no real Bluetooth hardware needed — same approach as `DrawServiceTests`, and now actually built that way (see above). Steps 1–3 (real BLE send/receive) fundamentally need real hardware and are human-verified only, exactly like the dropped ultrasonic Phase 7 was flagged as "not agent-verifiable" — that constraint doesn't go away with the BLE pivot, it just moves to different hardware, and is why steps 1–2 below are still untouched.

### Track B: ultrasonic presence sensing (added 2026-10-19, build and test alongside BLE, not instead of it)

the maintainer's call, 2026-10-19: build **both** detection tracks and compare them on real hardware himself, rather than deciding on paper which one wins. Trigger: he found `https://ultramodem.ronen.in/` (`github.com/ronen6999/ultramodem`), a browser-based near-ultrasonic data link (binary FSK, 18500 Hz = `0` / 19500 Hz = `1`, ~20 bit/s, XOR checksum only, no FEC/retry, max 64 chars), and asked whether it revives the ultrasonic room-detection idea dropped on 2026-08-28.

**Assessment of that project (for the record, this is an opinion, not a measurement):** it does not demonstrate what we'd need. It is a deliberate, human-held, one-pair, quiet-room *data transfer* toy — no amplitude-to-distance metric, no multi-device collision handling, and the author states the tone is "audible to most people" even at those frequencies. None of that proves or disproves whether continuous, unattended, multi-PC amplitude sensing is viable here — it just sidesteps the exact problems (ambient noise, mic/speaker placement/quality, reflections) that killed the original ultrasonic Phase 7. Noted so the reasoning is on record; **the maintainer wants both tracks built and tested empirically regardless, not re-decided from this analysis alone** — that is his call to make, not something to re-litigate at planning time.

**Design — deliberately not a port of ultramodem's protocol.** Ultramodem's FSK/checksum/bitrate exist to move a text payload; we don't need a data channel, only a per-pair proximity signal, same as the BLE track's RSSI. Porting FSK bit-encoding here would add complexity (symbol timing, checksum framing) that buys nothing for this use case. Proposed instead:

1. **Phase 0 — hardware/perception spike, do this FIRST, same spirit as the BLE Phase 0 spike:**
   - Does a single fixed near-ultrasonic tone (candidate: ~19 kHz, pick after checking the actual frequency response of the target PCs' built-in speakers/mics — cheap integrated hardware often rolls off well before 20 kHz, this must be measured, not assumed) survive office background noise through a **real** PC microphone at usable SNR?
   - Is a tone repeating every ~30s (matching the BLE report cadence) perceptible/annoying to anyone actually sitting near a PC, over a full work day, on the real target hardware? This is a human-judgment question, not something to assume answered either way from ultramodem's "audible to most, inaudible to some" framing.
   - Concretely: a throwaway spike exe, same pattern as the BLE one, playing a candidate tone and logging captured amplitude on two real PCs a room apart and a wall apart — plus the maintainer/a colleague just sitting near it for a while and saying whether they notice it.

2. **Collision handling — the one thing ultramodem never had to solve and we do:** multiple PCs cannot all chirp at once on one shared tone and expect a meaningful amplitude reading. Reuse the existing Chef-as-authority pattern (same shape as `BreakScheduler`/the BLE aggregation plan): the Chef publishes a deterministic round-robin order (e.g. sorted known `NodeId`s from `NodePresenceService.KnownNodes`) and a fixed slot duration; during its own slot, each node plays the single tone and every other node's listener records the amplitude it measured during that slot, attributed to that slot's known sender. Time-division, not frequency-division — no per-node frequency allocation needed, which also sidesteps tightly packing many sub-bands into a narrow near-ultrasonic range.
3. **Local sense loop, every node:** continuously-running microphone capture (`NAudio.Wave.WaveInEvent`, already have NAudio as a dependency for `GongPlayer`) + FFT magnitude at the chosen tone frequency, smoothed the same "short moving average, don't act on one instantaneous reading" way as the BLE RSSI plan. **Seam done (2026-10-19):** `IUltrasonicBeacon` (`Pausengong.Core/Audio/`, play-tone / listen-and-measure) + `FakeUltrasonicBeacon` (tests), same seam pattern as `IMqttNodeClient`/`IUdpDiscoveryTransport`. **Real NAudio-based implementation and the loop itself are not started** — deferred, not blocked the same way BLE is (no open API-availability question here, NAudio capture/playback doesn't care about packaging), but still needs real speaker/mic hardware to write and verify correctly, and the concrete tone frequency is a Phase 0 output, not something to guess at here.
4. **Reuse, don't duplicate, the aggregation/clustering math.** **Done (2026-10-19):** `NeighborReport.ObservedSignalByNodeId`, `NeighborEdge.SymmetrizedSignal`, and `ClusterCalculator.Cluster`'s `threshold` parameter are renamed from their old BLE-specific names (`ObservedRssiByNodeId`/`SymmetrizedRssi`/`thresholdRssiDbm`) — purely a rename, behavior unchanged, existing BLE tests updated in place. Both tracks now feed the same `NeighborGraphBuilder`/`ClusterCalculator`/`NeighborAggregatorService` pipeline. **Do not merge BLE and ultrasonic edges into one clustering pass** — dBm and tone-amplitude-ratio are different, incomparable scales; `NeighborAggregatorService` is instantiated once per track specifically so this can't happen by accident (see step 3 of the BLE "Suggested build order" above) — run two independent clusterings and let the maintainer compare the two *results* on real hardware, don't average their inputs.
5. **New MQTT surface, mirroring the BLE one. Done (2026-10-19):** `TopicSchema.NodeUltrasonicNeighbors(nodeId)`/`NodeUltrasonicNeighborsWildcard` (non-retained per-node report, same shape as `NodeBleNeighbors`) plus `TopicSchema.UltrasonicSchedule` (the Chef-published round-robin schedule topic). The schedule computation itself is also done: `UltrasonicRoundRobinSchedule` (model) + `UltrasonicRoundRobinScheduler.BuildSchedule` (`Pausengong.Core/Neighbors/`) — pure, deterministic (ordinal node-id sort), computes who transmits at any instant and when each node's own slot starts; fully unit tested (`UltrasonicRoundRobinSchedulerTests.cs`). **Not done:** nothing calls `BuildSchedule` from a running Chef yet, and nothing publishes/subscribes to `TopicSchema.UltrasonicSchedule` yet — that glue needs the real `IUltrasonicBeacon` implementation (step 3) to be worth wiring up.
6. **Feeding into rooms:** identical to the BLE track's step 6 — both are just alternate producers of candidate `RoomGroup`s under the existing `RoomModeConfig`/"automatisch" mechanism (still needs the UI toggle, see Suggested next steps). A real decision on whether the UI lets the maintainer pick BLE vs. ultrasonic vs. manual, or auto-prefers whichever one actually produced a result, is **not made yet** — surface this as an explicit choice when the UI toggle gets built, don't default it silently.

## Critical safety rule — do not break this

`Pausengong.Core/Config/TestModeState.cs` + `RingExecutor.cs` are the safety-critical gate: **test mode defaults to ON** on any fresh config, and only the toast/notification path may fire for scheduled/networked rings. The manual "Test-Gong" button is the *only* thing allowed to bypass this, and only from its own direct UI click handler — never from scheduling, config sync, or startup code. The user was explicit about this (real break-bell system, accidental real gong during dev/testing is genuinely disruptive). If you add new ring-triggering code, it must go through `RingExecutor.ExecuteRingAsync`, not call `IGongPlayer` directly.

## Non-obvious gotchas hit while building this (read before re-deriving)

- **MQTTnet 5.x has no managed/auto-reconnect client** — `MQTTnet.Extensions.ManagedClient` stopped being published after 4.3.7 and doesn't exist for v5. Reconnect policy is hand-rolled in `ChefElectionService` (driven by `MqttNodeClient.Disconnected`), which is actually correct here since after a Chef dies you need to re-run discovery, not blindly retry the dead server.
- **WinUI3 `Window` is not a `FrameworkElement`** — `x:Bind` with a `Converter=` on anything hosted directly in a `Window`'s XAML crashes natively (`0xc000027b` in `Microsoft.UI.Xaml.dll`, no useful .NET exception). Fix: host all real content in a `Page` (`MainPage`, `SettingsPage`), keep `Window` XAML nearly empty, set `Content = new SomePage(...)` in code-behind.
- **Missing `XamlControlsResources` merge in `App.xaml`** causes the same native crash class the moment a `ThemeResource` like `CardStrokeColorDefaultBrush` is referenced (e.g. `BorderBrush` on a `ListView`). Must merge `<XamlControlsResources xmlns="using:Microsoft.UI.Xaml.Controls" />` in `App.xaml` resources — normally scaffolded automatically by the VS project template, which we don't have here.
- **`x:DataType` on a BCL value type (e.g. `TimeOnly`) in a `DataTemplate`** is unstable — crashed (same `0xc000027b` signature) the moment the template actually got instantiated (i.e., only when the list went from empty to non-empty, not on load). Avoid; use the default `ToString()` rendering (works fine, already proven) or a wrapper view-model type instead.
- **`dotnet publish -p:PublishSingleFile=true` silently drops plain `<Content>` items** (tested repeatedly, including with `CopyToPublishDirectory` set — didn't help) from the output — a `bin\...\win-x64` build has `Assets\gong.wav` etc., a single-file `publish\` output does not. Fixed by embedding these 4 files (`gong.wav`, `Logo.ico`, `Logo-256.png`, `Logo-44.png`) as `<EmbeddedResource>` with explicit `<LogicalName>`, extracted once to `%LocalAppData%\Pausengong\assets\` on first run (`AssetExtractor.cs`). If you add new runtime assets, embed them the same way — don't add more loose `<Content>` files expecting them to survive single-file publish.
- **Multiple instances on one PC fight over the same UDP 49531 / MQTT 18830 ports** and the losing instance's startup exception was previously swallowed silently (fire-and-forget `Task`, not routed through `Application.UnhandledException`), leaving the UI stuck forever on "Netzwerk wird gesucht …" with zero indication anything failed. Fixed two ways: (1) a named `Mutex` in `App()` refuses a second launch outright (shows a native `MessageBox`, points at the tray icon); (2) `MainPage.StartNetworkingAsync` now has a top-level `try/catch` that surfaces the failure in `MainViewModel.NextGongTargetText` (the subtitle line under the "Pausengong" title) and logs to `%LocalAppData%\Pausengong\logs\`. If you see "Netzwerk-Start fehlgeschlagen: ..." in the UI, that log has the real exception.
- There's also an app-wide `Application.UnhandledException` handler (logs + `e.Handled = true`) as a last-resort safety net for UI-thread exceptions specifically — it does **not** catch background `Task` exceptions (different mechanism), which is why the fix above was still needed separately.
